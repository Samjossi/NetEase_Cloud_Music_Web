# Zoo Code Memory Bank 轻量版指导文档

> **版本**：v1.0（轻量版）  
> **适用**：Zoo Code（Roo Code 社区继任版）  
> **目标**：通过双文件外部记忆系统，消除 AI 的上下文重建延迟，维持跨会话心流连续性，同时避免记忆本身成为认知负担

---

## 一、核心原理

Zoo Code 的上下文窗口是有限的。当任务变长、项目变复杂时，AI 会"失忆"——它不记得昨天为什么排除了二值化方案，也不记得当前卡在哪个参数上。每次重启 VS Code 或开启新任务，AI 都需要重新"认识"你的项目，这产生大量**认知对齐成本**。

Memory Bank 是一套**项目级持久化记忆协议**：把项目状态、决策写入项目根目录下的 `memory-bank/` 文件夹中。Zoo Code 每次任务开始时自动读取，结束时自动更新。相当于给 AI 外挂了一块**非易失性存储**。

**轻量版核心思想**：Memory Bank 是上下文窗口不足时的工程补丁，不是记忆机制的范式突破。在高度实验性、多模块并行、性能敏感的项目中，应裁剪文件数量至最少，降低维护面，避免记忆本身成为认知负担。

---

## 二、轻量级 Memory Bank 协议（双文件版）

### 2.1 文件结构

初始化完成后，你的项目根目录应出现以下结构：

```
你的项目/
├── memory-bank/
│   ├── context.md      ← 动态更新，记录"现在卡在哪、下一步做什么"（< 500 tokens）
│   └── decisions.md    ← 半静态，记录"不可逆的架构决策"
└── .clinerules         ← 精简版记忆协议
```

### 2.2 各文件职责

| 文件 | 何时更新 | 存什么 | 示例（仿生视觉项目） |
|------|---------|--------|-------------------|
| `context.md` | 每次任务后 | 当前思路、阻塞点、下一步 | "V2 引擎 Association Field 卡在轮廓竞争抑制参数，目标 10 FPS" |
| `decisions.md` | 做决策后 | 不可逆决策及原因 | "排除二值化，采用连续值保留微信息；选用 Monogenic PC 而非 CMPC" |

### 2.3 为什么只保留两个文件

- **技术栈、依赖版本** → 从 `pyproject.toml`、`requirements.txt` 或代码本身推断，无需重复记录。
- **代码组织规则** → 从目录结构推断，AI 具备代码理解能力。
- **已完成清单** → 从 git log 和代码注释推断，避免人工维护与代码实际状态错位。
- **待办清单** → 只保留在 `context.md` 的"下一步行动"中，限制在 3 项以内，防止清单膨胀。

## 三、初始化指令（直接复制给 Zoo Code）

将以下整段文字粘贴到 Zoo Code 的聊天框中，按回车发送。AI 会自动完成所有创建和配置工作。

```
请为这个项目初始化轻量级 Memory Bank。操作如下：

1. 在项目根目录创建 memory-bank/ 目录。
2. 创建以下文件并写入当前已知的项目状态（基于我们之前的对话和当前代码库推断，每个文件控制在 20 行以内）：
   - context.md → 当前正在处理什么、核心思路、阻塞点、下一步行动
   - decisions.md → 已确定的不可逆架构决策及选择原因（如技术选型、排除方案）

3. 如果项目根目录没有 .clinerules 文件，请创建一个，并写入：
   "Before starting any task, read memory-bank/context.md and memory-bank/decisions.md.
   After completing any task, update these files if the project state or decisions have changed.
   Keep entries concise. Append new decisions with timestamps. If a decision is reversed, mark it [DEPRECATED] but keep it."

4. 完成后，把创建的文件列表和每个文件的内容摘要发给我确认。
```

## 四、人工审核清单（第一次初始化后必做）

AI 自动初始化后，请花 3 分钟检查以下事项：

- [ ] `context.md` 中的"当前阻塞点"是否准确？
- [ ] `context.md` 的"下一步行动"是否遗漏了正在进行的子任务？（限制 3 项以内）
- [ ] `decisions.md` 是否包含你已经确定但 AI 可能不知道的关键决策？
- [ ] `.clinerules` 是否包含"读取 → 更新"的强制协议语句？

**如有错误，直接对 AI 说**："请修正 `memory-bank/xxx.md`，第 X 条应该是……"

## 五、日常使用协议（关键检查点机制）

轻量版不主张"每次任务后都更新"，而是只在以下**关键检查点**触发写入：

| 检查点类型 | 触发条件 | 更新内容 |
|-----------|---------|---------|
| 子模块完成 | 一个可交付模块通过测试（如 V1 可微模块） | context.md 移除该模块的阻塞/待办 |
| 不可逆决策 | 选定部署硬件、排除某个算法路线 | decisions.md 追加新决策 |
| 重大阻塞 | 发现预计持续 24 小时以上的问题（如 1.6 秒/帧的性能瓶颈） | context.md 更新阻塞描述 |
| 上下文切换 | 从 V2 引擎切换到 RISC-V 部署 | context.md 更新当前工作上下文 |

**强制更新提示词**（在检查点发送）：

```
检查点到达，请更新 Memory Bank：
1. context.md：当前阻塞点是否变化？下一步行动是否调整？
2. decisions.md：本次任务是否产生新的不可逆决策？
更新后停止，等待我确认。
```

## 六、故障处理：AI 偷懒不更新 Memory Bank

### 方案 A：在 `.clinerules` 中加入强制条款

确保 `.clinerules` 包含以下段落（初始化时 AI 应已写入，如缺失请手动补充）：

```markdown
## CRITICAL: Lightweight Memory Bank Rule
You MUST read memory-bank/context.md and decisions.md BEFORE generating any code.
You MUST update these files at key checkpoints (submodule complete, irreversible decision, major blocker, context switch).
If you fail to update, the next session will lose critical context and rebuild from scratch.
```

### 方案 B：任务结束时主动提醒

在每次任务收尾时，发送：

```
任务结束，请更新 Memory Bank 后再停止。确保：
1. context.md 反映当前最新状态
2. 如有新决策，追加到 decisions.md
```

### 方案 C：版本控制兜底

将 `memory-bank/` 纳入 git 版本控制（不要忽略）。这样：
- 你可以 diff 查看 AI 每次更新了什么
- 如果 AI 写乱了，可以 `git checkout` 回滚
- 换机器时记忆随代码同步迁移

```bash
git add memory-bank/ .clinerules
git commit -m "checkpoint: memory bank update"
```

## 七、工作流适配评估

不同项目特征对 Memory Bank 的适配度差异显著。以下帮助你判断轻量版是否适合你。

| 特征 | 适配度 | 原因 |
|------|--------|------|
| 项目周期短、决策链不深（< 20 条） | ✅ 高 | 状态空间小，重复对齐成本降低最明显 |
| 团队只有一个人 + AI | ✅ 高 | 无人类协作者导致记忆失步，文件状态即 ground truth |
| 架构相对稳定 | ✅ 高 | 技术栈和目录结构不频繁变动，减少噪音 |
| 代码库规模超过上下文窗口 50% | ⚠️ 边际递减 | 根本问题是窗口太小，Memory Bank 只是重新排列 token 优先级，未增加容量 |
| 高度探索性、方向频繁变更 | ⚠️ 轻量版可缓解 | 只保留不可逆决策，避免过时决策噪音累积 |
| 性能敏感、优化细节密集 | ⚠️ 轻量版可缓解 | context.md 保留具体阻塞，减少摘要损失 |
| 多人类协作者 | ❌ 低 | 人类不更新 Memory Bank，AI 基于 stale 信息决策，错误率上升 |
| 多模块并行（V1/V2/部署） | ⚠️ 中等 | 单文件 context 即可覆盖，无需分层配置 |
| 跨学科（神经科学 + 工程） | ✅ 高 | 需要持久化领域知识（如 Monogenic PC 参数含义、相位一致性算法边界） |
| 习惯用 MD 文档规范 Agent | ✅ 高 | 工作流契合，认知摩擦低 |

**结论**：轻量版 Memory Bank 对多模块并行、高度实验性、性能敏感的项目**部分有效**，但不应作为唯一记忆策略。建议与代码自描述、git log 形成互补。

## 八、进阶：与 CARTS 概念存储的衔接

如果你正在设计内容寻址的记忆系统（如 CARTS），可将轻量级 Memory Bank 视为**粗糙原型**：

- `decisions.md` → 类比回忆层（按时间索引）
- `context.md` → 类比工作记忆（当前激活状态）
- 当条目超过 50 条，线性文件系统的检索效率崩溃，这正是你需要从"路径寻址"迁移到"内容寻址"（哈希/语义检索）的信号。

## 九、轻量版 vs 完整版对比速查

| 维度 | 完整版（五文件） | 轻量版（双文件） |
|------|----------------|----------------|
| 文件数 | 5 + .clinerules | 2 + .clinerules |
| 维护成本 | 高（每次任务更新） | 低（检查点更新） |
| 适合项目周期 | 2-8 周 | 2-16 周 |
| 适合决策链深度 | 浅（< 20 条决策） | 深（可回溯，decisions.md 即日志） |
| 适合代码库规模 | < 5 万行 | < 15 万行 |
| 适合探索性 | 低（变更频繁时日志膨胀） | 高（只保留不可逆决策） |
| 性能敏感项目 | 差（细节丢失在摘要中） | 较好（context 保留具体阻塞） |
| 多模块并行 | 需分层配置 | 单文件 context 即可覆盖 |
| 与 git 协同 | 需要 | 必需（进度从 log 推断） |

---

## 十、一句话总结

> Memory Bank 不会加速模型推理，但会把每次交互的**上下文对齐成本**从几分钟压到几秒。轻量版通过裁剪至双文件、检查点更新，把维护成本压到最低，让记忆服务于工作流，而非工作流服务于记忆。
