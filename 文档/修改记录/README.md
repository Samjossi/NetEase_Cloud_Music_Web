## 📝 文档编写规范

### 归档声明要求

**⚠️ 强制要求**：本目录下的所有文档必须在文件头部添加归档声明，格式如下：

```markdown
> ⚠️ **归档声明**：本文档为历史快照，记录了特定时间点的决策与实施状态。
> 当前代码状态以对应 `.py` 源文件为准，本文档内容可能已过时，仅供参考。
```

**说明**：
- 归档声明必须放在文档的**最开头**（在标题之前）
- 措辞必须完全一致，不得自行改写
- 确保所有 AI 和人类读者获得统一警示
- 此目录下的文档一律视为历史快照，不代表当前代码状态

**参考**：详见 [`文档/文档编写规范.md`](文档/文档编写规范.md)

## 阅读须知

1. **历史快照性质**
   - 每份文档标题中的日期（如 `2026-05-16-...`）标识了该记录的撰写时间
   - 文档中提到的"已知问题"、"待修复项"、"TODO"仅在该时间点成立
   - 后续可能已被修复、废弃或变更，**切勿以文档内容推断当前代码状态**

2. **代码状态以源代码为准**
   - 判断当前代码是否有某问题，应直接查看对应 `.py` 源文件
   - 不应以历史修改记录中的描述作为当前状态依据

3. **TODO 列表已过期**
   - 文档末尾的待办清单（`- [ ]`）属于当时的实施计划
   - 完成后可能未在本文档中打勾更新
   - 当前真实待办应以最新计划或项目管理工具为准

4. **引用规范**
   - 如需引用本文档内容，必须同时标注日期，例如：
     > "根据 2026-05-16 的实施记录，当时存在...（已修复/已变更）"

## 何时查阅本文档

- ✅ 追溯某功能的设计决策历史
- ✅ 了解某项变更的实施背景和方案对比
- ✅ 排查"为什么当时这样设计"
- ❌ 判断当前代码是否有某 bug
- ❌ 作为当前代码状态的唯一依据
- ❌ 作为当前待办事项清单
