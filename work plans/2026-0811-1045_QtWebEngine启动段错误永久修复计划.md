# QtWebEngine 启动段错误永久修复计划

> **状态**：已实施
> **范围**：`profile_manager.py`、`main.py`（QtWebEngine 启动崩溃防御与可观测性）
> **时间**：2026-08-11 10:45（UTC+8，设计）/ 2026-08-11 10:56（实施）
> **优先级**：高

---

## 1. 背景与问题定位

### 1.1 故障现象

2026-08-11 10:35 起，应用在 Zen Studio 集成终端以 `uv run main.py` 启动，窗口出现后随即闪退，连续 4 次必现；之后又自行恢复正常，连续 4 次运行无任何异常。

### 1.2 已确认的事实

| 证据 | 结论 |
|:---|:---|
| 日志全部走完初始化，终止于 `页面开始加载`，无 `load_finished` | 崩溃点在 QtWebEngine 页面加载阶段 |
| 复现退出码 139（SIGSEGV），stderr 无任何输出 | 原生层硬崩溃，Python 日志捕获不到，属"无声闪退" |
| 当前 `LD_LIBRARY_PATH` 为空 | 与 `2026-0811-0841_集成终端环境变量污染问题报告_ZenStudio.md` 的环境污染无关（该问题是 `ImportError`，有明确报错） |
| 崩溃前仅有 16 个打包/开发工具被 uv 重装，PySide6 未变动 | 与依赖版本变化无关 |
| 连崩 4 次后突然自愈 | 符合"脏 GPU 缓存被 Chromium 自动清理后恢复"的特征 |

### 1.3 根因推断（未完全证实）

Profile 持久化目录（`~/.local/share/netease-music/login_data`）下的 GPU 相关缓存（`GPUCache`、`DawnGraphiteCache`、`DawnWebGPUCache`）在此前异常退出（崩溃、强杀、环境污染期崩溃）时写入脏数据；后续启动时 QtWebEngine 读取脏缓存，在渲染/GPU 进程中触发段错误，形成"崩溃 → 缓存更脏 → 再崩溃"的循环，直至 Chromium 自行废弃缓存。

⚠️ 未拿到崩溃堆栈（无 coredump 记录），根因为推断。本计划的核心防御机制不依赖该推断成立——无论段错误具体诱因是什么，"异常退出后清理 GPU 缓存"都能把故障从"崩溃循环"降级为"最多崩一次"。

### 1.4 修复目标

- 异常退出后下次启动自动清理 GPU 缓存，杜绝崩溃循环；
- 原生崩溃在日志中留下可追溯痕迹（当前完全无记录）；
- 正常退出不受影响，不清缓存、不损渲染性能。

## 2. 修复思路总览

三层结构，前两层本次实施，第三层仅作预案：

| 层 | 机制 | 作用 | 本次实施 |
|:---|:---|:---|:---:|
| 防御层 | 异常退出标记 + 启动时 GPU 缓存自愈 | 崩溃最多发生一次，下次启动自动恢复 | ✅ |
| 观测层 | `faulthandler` 接管 SIGSEGV，写入 `logs/crash.log` | 崩溃留痕，支撑后续根因分析 | ✅ |
| 缓解层 | 预设 Chromium 开关（禁用 GPU 着色器磁盘缓存） | 若防御层实施后仍复发，兜底禁用问题缓存 | ❌ 预案 |

---

## 3. 实施步骤

### 3.1 `profile_manager.py`：新增异常退出守卫

在 `ProfileManager` 所在模块新增模块级函数（不改动现有类接口）：

```python
# profile_manager.py
# 新增常量与函数
RUNNING_MARK_FILE = ".netease_running"
GPU_CACHE_DIRS = ("GPUCache", "DawnGraphiteCache", "DawnWebGPUCache")

def check_abnormal_exit_and_recover(storage_path: str) -> bool:
    """启动早期调用。若检测到运行标记残留（上次异常退出），
    清理 GPU 相关缓存目录，返回是否执行了清理。"""

def create_running_mark(storage_path: str) -> None:
    """创建运行标记文件，内容为启动时间，供排查用。"""

def remove_running_mark(storage_path: str) -> None:
    """正常退出时删除标记文件。"""
```

要点：

- `check_abnormal_exit_and_recover` 必须在 QtWebEngine 初始化**之前**调用（即创建 `NetEaseMusicWindow` 之前），否则清理时机太晚；
- 仅删除 `GPU_CACHE_DIRS` 三个目录，**严禁触碰** `Cookies`、`Local Storage` 等登录态数据；
- 删除操作逐目录 `try/except`，失败仅记 warning，不阻断启动；
- 清理动作记 INFO 日志（"检测到上次异常退出，已清理 GPU 缓存：..."），无残留标记时静默跳过。

### 3.2 `main.py`：接线与崩溃留痕

两处改动：

```python
# main.py
# 1) 日志系统初始化成功之后、创建 QApplication 之前
import faulthandler
_crash_log = open("logs/crash.log", "a", buffering=1)
faulthandler.enable(_crash_log)

from profile_manager import (
    check_abnormal_exit_and_recover, create_running_mark, remove_running_mark
)
storage_path = os.path.expanduser("~/.local/share/netease-music/login_data")
recovered = check_abnormal_exit_and_recover(storage_path)
create_running_mark(storage_path)
```

```python
# main.py
# 2) app.exec() 返回后的清理段，cleanup_profile_manager() 之前
remove_running_mark(storage_path)
```

要点：

- `logs/` 目录沿用现有日志目录约定（由 `init_logging` 保证存在）；
- `_crash_log` 句柄保持到进程结束，不主动关闭；
- 存储路径与 `ProfileManager.__init__` 的默认取值逻辑保持一致（含 `NETEASE_LOGIN_DATA_PATH` 环境变量覆盖分支），避免两处路径分叉——实施时优先复用 `ProfileManager` 的路径解析，而非复制 `expanduser` 字面量；
- 正常退出路径已有 `closeEvent` 托盘最小化逻辑，需确认"最小化到托盘"不触发 `app.exec()` 返回（现状如此，标记仅在真正退出时移除）。

## 5. 风险与注意点

| 风险 | 说明 | 对策 |
|:---|:---|:---|
| 清理后首次渲染变慢 | 着色器缓存需重新编译，首屏可能轻微卡顿 | 仅在异常退出后触发，正常路径零开销，可接受 |
| 误删登录态数据 | 清理范围若扩大将强制用户重新登录 | 白名单制，仅三个 GPU 缓存目录名，验收清单专项回归 |
| `faulthandler` 只能给 Python 线程栈 | 原生堆栈仍需 gdb/coredump | 已在日志留 Python 侧现场；若复发再补 coredump 采集 |
| 根因推断错误 | 段错误也可能由 GPU 驱动/QtWebEngine 缺陷引发，与缓存无关 | 防御层不依赖推断成立；复发时启用 §6 预案并升级分析 |

---

## 6. 预案（本次不实施）

若防御层实施后仍观察到段错误复发（以 `logs/crash.log` 为准），按序升级：

1. `main.py` 顶部设置 `QTWEBENGINE_CHROMIUM_FLAGS="--disable-gpu-shader-disk-cache"`，永久绕过着色器磁盘缓存（性能代价小于 `--disable-gpu`）；
2. 仍无效则采集 coredump / gdb 堆栈，定位真实崩溃点，再评估 `--disable-gpu` 或 PySide6 版本升级。

---

## 7. 不实施项

- 默认禁用 GPU 加速（影响视频渲染性能，且无证据必要）；
- 定期/每次启动清理缓存（无端损失性能）；
- 守护进程/watchdog 自动重启（闪退发生在用户眼前，自愈已足够，自动重启会掩盖问题）；
- 升级 PySide6/Qt 版本（无证据指向版本缺陷）。
