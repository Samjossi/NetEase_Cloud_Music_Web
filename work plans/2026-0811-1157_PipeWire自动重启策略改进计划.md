## 1. 背景

当前 PipeWire 自动重启系统采用**固定周期策略**（每16首歌或每N分钟），无论 PipeWire 实际状态如何都执行重启。这种方式有两个问题：

- **治标不治本**：没有定位内存泄漏的根因，只是定期清空积累的垃圾。
- **过度重启**：即使 PipeWire 状态健康也照常重启，造成不必要的播放中断。

2025年12月初次实现时，系统运行在 PipeWire 0.3.x，该版本已知存在长时间运行的内存泄漏。当前系统已升级至 **PipeWire 1.0.5**（libpipewire 1.0.5，Ubuntu 24.04 官方包），1.0 系列修复了大量泄漏问题，固定周期重启的合理性需要重新评估。

相关文档：`2025-1201-1953_PipeWire自动重启功能完成报告.md`

## 3. 改进方案

### 3.1 方案：内存阈值触发重启（推荐）

不再按歌曲数或时间间隔，而是监控 PipeWire 进程的 **RSS（常驻内存）**，仅在超过阈值时触发重启。

**监控逻辑**：

```python
# pipewire_manager.py 新增方法
import subprocess

def get_pipewire_memory_mb(self) -> float:
    """获取 PipeWire 进程当前 RSS 内存（MB）"""
    try:
        result = subprocess.run(
            ["ps", "-o", "rss=", "-C", "pipewire"],
            capture_output=True, text=True, timeout=5
        )
        if result.stdout.strip():
            rss_kb = sum(int(line) for line in result.stdout.strip().split())
            return rss_kb / 1024
    except Exception:
        pass
    return 0.0
```

**触发策略**：

- 阈值：RSS 超过 **500 MB** 时触发
- 检查频率：每分钟一次（复用现有 timer）
- 冷却时间：重启后至少间隔 30 分钟，防止频繁重启
- 记录日志：每次检查记录内存值，便于事后分析

**优点**：
- 改动量小（约 30 行新增/修改）
- 健康状态下零重启
- 兼容现有架构，不影响托盘通知等

### 3.2 观察期策略

在实现方案 3.1 之前，建议先用 **1-2 周观察 PipeWire 1.0.5 的实际表现**：

- 关闭周期性重启
- 手动用 `ps -o rss= -C pipewire` 定期查看内存趋势
- 若 1.0.5 确实不再泄漏，则整个重启系统可退役

## 5. 风险与回滚

| 风险 | 影响 | 缓解 |
|---|---|---|
| 阈值设置不当导致频繁重启 | 用户体验下降 | 从 500MB 起步，观察后调整；冷却时间兜底 |
| `ps` 命令在不同系统上输出格式不同 | 内存读取失败 | `try/except` 保护，失败时跳过本轮检查 |
| PipeWire 1.0.5 已不需要重启 | 开发浪费 | 观察期先行，确认必要性后再开发 |

回滚方式：恢复固定周期策略或关闭功能，修改仅限于 `pipewire_manager.py` 和 `pipewire_manager_integration.py`，无数据库/配置文件破坏性变更。
